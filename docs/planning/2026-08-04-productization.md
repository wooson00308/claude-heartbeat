# 하트비트 프로덕트화 개선 계획

작성: 2026-08-04. 트리거는 이날 workflow-labs 도그푸딩 중 실측으로 잡힌 사고 두 건이다.

- 사고 1 — 크로스 프로젝트 잡 증발: 소비자 앱(LLM Workflow)이 mech-arena 프로젝트에서 역할 잡을
  설치하자 전역 `HEARTBEAT.md`의 관리 블록이 통째로 다시 쓰이며 workflow-labs 잡 3개가 사라졌다.
  사용자 커스텀 값(interval·timeout·max_per)도 함께 소실. 원인의 절반은 앱의 병합 로직이지만,
  근본 원인은 데몬이 "여러 프로젝트가 한 파일을 나눠 쓰는" 구조를 강요한다는 것.
- 사고 2 — 전역 틱 블로킹: mech-arena 기획자 세션이 도는 동안(최대 timeout 20m) 메인 루프가
  모든 slug 그룹의 완료를 기다리느라 workflow-labs를 포함한 전 프로젝트의 다음 tick이 밀렸다.
  `heartbeat_loop`의 `with ThreadPoolExecutor(...)` 블록이 사이클마다 배리어를 만든다.

## 목표

1. 프로젝트별 관리가 안전할 것 — 한 프로젝트의 설치·수정·삭제가 다른 프로젝트에 영향을 못 주는 구조.
2. 실행 병렬화의 기반을 만들 것 — 프로젝트 간 완전 독립 스케줄, 프로젝트 내 병렬은 옵트인.
3. 외부 도구(앱·스크립트)가 기댈 수 있는 계약을 문서로 고정할 것 — 프로덕트화의 전제.

## 비목표

- 소비자 앱(LLM Workflow) 쪽 수정. 앱의 병합 버그·쓰기 대상 전환은 그 저장소의 별건이다.
- 같은 slug 잡의 기본 동작 변경. 프로젝트 내 직렬(파일 충돌 회피)은 기본값으로 유지한다.

## P0-A. 설정을 프로젝트별 파일로 분리 (jobs.d)

지금: `~/.claude/HEARTBEAT.md` 하나에 모든 프로젝트의 잡이 산다. 외부 도구가 자기 잡만 갱신하려면
마커 블록·병합·베이스라인 대조 같은 장치를 스스로 만들어야 하고, 오늘 그 장치가 실패했다.

변경:

- `~/.claude/heartbeat/jobs.d/<slug>.md` — 프로젝트당 파일 하나. 형식은 기존 잡 문법 그대로
  (`## 잡이름` + `- key: value`). 파일 안의 잡은 그 slug 소속으로 강제한다(`- slug:` 줄 불일치 시
  경고 후 파일 값 우선).
- `~/.claude/HEARTBEAT.md` — 전역 설정(`- tick:`)과 하위호환용 잡 정의. 계속 파싱한다.
  jobs.d와 이름이 겹치면 jobs.d가 이기고 경고 로그를 남긴다.
- `heartbeat migrate` — 기존 HEARTBEAT.md의 잡을 slug별로 jobs.d에 쪼개 쓰고, 원본에는 전역
  설정만 남긴다. 실행 전 원본을 백업한다.
- 계약 문서 `docs/config-contract.md` — 파일 위치·문법·잡 이름 규칙(상태 키!)·병합 우선순위를
  명시하고 semver로 안정성을 보장한다. 외부 도구는 "자기 slug 파일 하나를 통째로 쓴다"만 하면
  된다. 마커 블록·부분 병합이 계약에서 사라진다.

효과: 사고 1 계열이 구조적으로 불가능해진다. 쓰기 주체가 파일 단위로 격리되기 때문.

## P0-B. 스케줄러 배리어 제거

지금: 사이클마다 due 잡을 모아 slug 그룹별 스레드로 돌리고, 전 그룹 완료까지 기다린 뒤 tick을 잔다.
한 그룹의 장기 실행이 전체 스케줄을 세운다(사고 2).

변경:

- 상주 executor + 논블로킹 디스패치. 매 tick마다 due 판정만 하고, 그룹 실행은 제출만 한 뒤 바로
  다음 tick으로 넘어간다.
- in-flight 가드: 실행 중인 slug 그룹은 due여도 건너뛴다(같은 잡·같은 그룹의 중복 실행 금지 유지).
  그룹 종료 시 가드 해제.
- last_run 의미는 유지(완료 시각 기준). 단, 이번에 tick 루프가 가벼워지므로 condition-skip이
  last_run을 갱신해 interval이 밀리는 기존 절충은 그대로 둬도 비용이 없다 — 문서에만 명시.

효과: 프로젝트 간 실행이 진짜로 독립된다. A 프로젝트의 30분짜리 세션이 B 프로젝트의 10분 주기를
건드리지 못한다.

## P1-A. 프로젝트 내 병렬 옵트인

- jobs.d 파일(또는 잡)에 `parallel: N` 전역 키. 기본 1(현행 직렬 유지).
- N>1이면 그 slug 그룹 안에서 due 잡을 최대 N개 동시 실행. 같은 잡의 중복 실행은 여전히 금지.
- 소비자 쪽 준비가 된 프로젝트만 켠다. workflow-labs는 lease 선점(배타적 생성)과 `depends_on`
  직렬화가 이미 계약에 있어 첫 적용 후보다.

## P1-B. 관측성 — 병렬을 위한 UX의 실체

- state.json에 `running` 기록: 잡 시작 시 `{job, pid, started_at}` 추가, 종료 시 제거.
  비정상 종료 잔재는 pid 생존 확인으로 정리.
- `heartbeat status` CLI: 잡별 마지막 결과·다음 due·쿼터 사용량(창 안 실측)·지금 실행 중 여부를
  한 표로. 외부 앱이 pid 파일 하나로 데몬 생존만 보던 것을 잡 단위 실시간 상태로 끌어올린다.
- 알림에 실행 중 겹침 정보 포함(병렬 켠 프로젝트에서 "지금 2개 돌고 있음"이 보여야 한다).
- 조건 사유 캡처: condition의 stdout 첫 줄을 skip 시에도 state.json에 `last_condition_output`으로
  저장하고 `heartbeat status`와 로그에 싣는다. 지금은 조건 스크립트가 exit code만 내고 데몬도
  "condition 불충족"만 남겨, 소비자 화면에서 "왜 건너뛰었는지"가 세 층(스크립트→데몬→앱) 모두에서
  증발한다(2026-08-04 실측: 아이디어가 쌓였는데 카드는 사유 없는 "건너뜀"만 표시). 사유를 내는
  것은 조건 스크립트 소유자의 선택이고, 데몬은 통로만 보장한다.

## P2. 프로덕트 완성도

- quota 스킵 시 낡은 사유 잔존: 실행 한도 분기(`_quota_exceeded` 경로)가 `last_condition_output`을
  지우지 않아, 한도 소진으로 건너뛴 잡에 이전 스킵의 사유가 남는다. 소비자(workflow-labs SPEC-023)는
  quota_skipped에 사유를 표시하지 않는 것으로 우회 중 — 근본 수정은 이쪽. (2026-08-04 소비자 기획 중 발견)

- 로그 로테이션 버그: 파일 핸들러가 데몬 시작일 이름으로 고정돼 8/4 로그가
  `heartbeat_20260803.log`에 쌓이는 것을 실측. `TimedRotatingFileHandler`로 교체.
- 서비스 정체성 표준화: launchd 라벨이 설치 경로마다 다르다(실측: `com.catze.dream-heartbeat`).
  표준 라벨 하나(`com.claude-heartbeat`)로 통일하고 마이그레이션 안내.
- 상태 gc: 잡 정의가 사라진 state.json 항목(옛 전역 잡 이름, 지운 dream 잡 등) 정리 명령.
- `heartbeat check`: 설정 lint. 지금은 잘못된 interval이 조용히 3600으로 좌초한다 — 파일·줄을
  짚어 거부 사유를 말하게 한다.
- Windows 검증: 소비자 쪽(SPEC-015)이 Windows를 여는 중. jobs.d·스케줄러 변경분의 Windows
  동작을 테스트 러너로 고정.

## 리스크

- jobs.d 분리는 소비자 앱의 쓰기 대상 변경을 유발한다. 0.8은 하위호환이므로 앱이 늦게 따라와도
  동작은 하지만, 마커 블록 경로가 남아 있는 동안 사고 1 계열은 재발 가능하다. 앱 쪽 후속(자기
  slug 파일 쓰기로 전환)을 workflow-labs 아이디어로 등록해 짝을 맞춘다.
- 배리어 제거는 실행 타이밍을 바꾼다. 기존에는 장기 실행이 다른 잡의 tick을 밀어 결과적으로
  전역 직렬에 가까웠다 — 제거 후 실제 동시 실행 수가 늘며 claude 세션이 겹칠 수 있다. 쿼터
  (max_per)가 총량을 이미 막고 있고, 같은 slug는 여전히 직렬이므로 파일 충돌 면은 그대로다.
